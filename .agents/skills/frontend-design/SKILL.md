# Frontend Design

把 Antigravity 批准的独立视觉身份落实为可运行、响应式且可访问的前端。保留其创意主张，不套用与内容无关的通用模板，也不以 Codex 的偏好重开设计方向。

## 强制三阶段职责

先读取并遵守 `antigravity-codex-web-workflow`。本 Skill 只执行 Stage 2：增加技术可行性、建立实际框架、制作前端并做初步检查。

- Antigravity 独占 Stage 1 创意方案和设计定案。
- Codex 不得在缺少已批准方案时自行补出网站创意、信息结构或关键交互。
- Antigravity 独占 Stage 3 完整验证和最终通过/失败判断。
- Codex 截图、浏览器 smoke、lint、构建和可访问性抽查只属于初步检查。

若缺少可实施的 Antigravity 方案，停止生产写入并报告 `STATUS: WAITING_FOR_ANTIGRAVITY_CREATIVE_PACKAGE`。

## 核心工作流

### 1. 锚定主题

先明确并简短陈述：

- **Subject**：产品、组织、人物或内容究竟是什么。
- **Audience**：谁会使用或阅读。
- **Single job**：页面最重要的一个任务。
- **Constraints**：框架、现有设计系统、性能、品牌与内容限制。

从 Antigravity 方案和已接受的项目资料中取得这些答案。若答案缺失到必须发明创意、内容结构或主要任务才能继续，返回 Stage 1；不要自行选择方向。始终使用真实业务内容，不要用无意义占位文案掩盖方案缺口。

### 2. 建立实现契约

把已批准的美学方向转成明确的工程契约，再开始编码。每一项实现选择都应能追溯到 Antigravity 方案、现有设计系统或用户明确批准的补充决定。

创建一套紧凑的 design tokens：

- **Color**：4–6 个具名色值，说明每种颜色的职责。
- **Type**：至少区分 display 与 body；需要数据或标注时再增加 utility 字体。
- **Layout**：用一句话描述版式逻辑，必要时用小型 ASCII wireframe 比较方案。
- **Signature**：记录 Antigravity 指定的标志性元素及其工程实现方式。

当方案留有工程自由度时，把复杂度集中在已批准的 signature；其余元素保持安静、精确和一致。需要改变 signature 或视觉主张时返回 Stage 1。

### 3. 做独特性审查

编码前审查设计方案：

- 这个方案换成另一个同类产品后是否仍然成立？若成立，说明还不够具体。
- 结构编号、眉题、分隔线、标签等是否编码了真实信息？若只是装饰，删除。
- Hero 是否表达页面主张，而不是默认的“大标题 + 指标 + 渐变强调”？
- 是否无理由落入常见默认风格：奶油底配衬线与陶土色、黑底配荧光色、密集报纸网格、白底紫蓝渐变？
- 动效是否服务主题与理解？若只是增加“高级感”，收敛或删除。

发现通用化选择时，优先恢复 Antigravity 方案的具体意图。若修正会改变已批准方向，先返回决策，不自行修改。

### 4. 实现设计

产出完整、可运行的代码，遵守用户指定的框架与项目约定。让所有颜色、字体、间距、圆角、阴影和动效都能追溯到已选方向。

重点执行：

- 用排版承载个性，建立明确的字号、字重、行高和字距层级。
- 让布局表达信息关系；可以不对称、重叠或打破网格，但必须保持阅读秩序。
- 优先编排一个有意义的进入、滚动或交互时刻，不堆砌零散动画。
- 控制 CSS specificity，避免类型选择器与组件类相互覆盖。
- 根据视觉目标匹配实现复杂度：极简需要精度，繁复需要完整层次。
- 需要具体工程规则时，读取 [references/implementation-checklist.md](references/implementation-checklist.md) 并逐项执行。

### 5. 设计界面文案

把文字视为设计材料：

- 从用户视角命名对象，不暴露系统内部实现。
- 使用主动语态和具体动词；按钮直接说明将发生什么。
- 在完整流程中保持动作名称一致。
- 让错误信息说明发生了什么以及如何修复，不含空泛道歉。
- 让空状态引导下一步行动。
- 让 label、example、description 各自只承担一个职责。

### 6. 初步检查成品

在环境允许时运行页面并截图检查桌面与移动视口。复审：

- 主题和主要任务能否在首屏被理解。
- 标志性元素是否真正独特且不过度。
- 是否存在字体回退、内容溢出、间距失衡或 CSS 冲突。
- 键盘焦点、对比度、语义结构和 reduced motion 是否可用。
- 是否有任何装饰不能解释其作用；删除一个最弱的元素后是否更好。

修正明显实现问题后，提交限定范围内的文件、推送评审分支、创建 Draft MR/PR，并提供包含精确评审 commit 的预览。默认把该 MR/PR 交给 Antigravity 做 Stage 3 完整验证；Antigravity 返回修正项时，在同一个开放 MR/PR 中提交更新并交回复测。如果用户明确说合并、发布或本次小 Bug 跳过 Antigravity，则完成与风险相称的最低检查后可以合并当前 MR/PR，并报告 `ANTIGRAVITY_PHASE_3: SKIPPED_BY_USER`。不要把“响应式、可访问、已复审”等初检结果或被跳过的检查描述为完整 QA 或最终通过。

## 输出要求

- 先用简短设计主张说明方向、tokens 与 signature，再提供实现。
- 尊重用户已经确定的品牌、内容和技术选择，不擅自重开方向。
- 不为展示效果引入无必要依赖。
- 无法运行或截图时，明确说明未验证的部分，不把静态检查描述为视觉验证。
- 交付时报告 `CODEX_PHASE_2: MR_READY_FOR_ANTIGRAVITY_VALIDATION | BLOCKED` 和真实的 `ANTIGRAVITY_PHASE_3: PENDING | PASS | FAIL | SKIPPED_BY_USER`，附上 MR/PR、精确评审 commit 与预览，并列出已运行和已跳过的检查。
